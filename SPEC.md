# ServCrafty – Technical Spec (source of truth for backend + frontend)

Monorepo (npm workspaces): `server/` (Fastify + TypeScript, ESM), `web/` (React + Vite + TS + Tailwind, PWA), `docker/`, `lxc/`.
Production: the server serves `web/dist` statically and the API under `/api`; WebSockets under `/ws`.

## Decisions (from the owner – do not change)
- Stack: Node 22+/TypeScript, Fastify, React+Vite. DB: **PostgreSQL** (external; `DATABASE_URL`), via `pg` + plain SQL migrations (`server/migrations/*.sql`, applied at boot, tracked in `schema_migrations`). No ORM.
- Servers run as sibling containers inside a **bundled privileged dockerd** (DinD) in the ServCrafty container. Docker access via `dockerode` on `DOCKER_HOST` (default unix:///var/run/docker.sock). Images: `itzg/minecraft-server` (Java, all types, CurseForge/Modrinth modpacks) and `itzg/minecraft-bedrock-server` (Bedrock).
- Server types: VANILLA, PAPER, PURPUR, FOLIA, SPIGOT, BUKKIT (CraftBukkit), FABRIC, QUILT, FORGE, NEOFORGE, BEDROCK, plus modpack sources CURSEFORGE and MODRINTH (itzg `TYPE=AUTO_CURSEFORGE` / `MODRINTH`).
- Network: host port mapping from an admin-defined pool (one game port per server; RCON/query stay internal on the docker network).
- Auth: cookie session (httpOnly, SameSite=Lax, signed) ; password (argon2id via `@node-rs/argon2`); TOTP (`otplib`, QR via `qrcode`); Passkeys (`@simplewebauthn/server` + `/browser`). Passkeys and TOTP are 2nd factors (and passkeys can also be a passwordless login if the user enabled one – keep to: password -> then 2FA step if enrolled). Admin created from env `ADMIN_USERNAME`, `ADMIN_PASSWORD` (and optional `ADMIN_EMAIL`) on first boot if no users exist. No public signup; admin creates users.
- Roles: `admin`, `user`. Admin sees/manages ALL servers. User sees own + shared. Per-server share levels: `viewer` (view, console read, stats), `operator` (+ power, console commands, players, backups run), `manager` (+ files, settings, mods, delete backups, share). Owner/admin = full.
- Quotas per user (nullable = unlimited): `max_servers`, `max_ram_mb` (sum), `max_cpu` (sum of cores, decimal), `max_disk_mb` (sum). Enforced at create/update server.
- CurseForge API key: stored encrypted (AES-256-GCM, key from `SECRET_KEY` env) in `settings` table, editable by admin; env `CURSEFORGE_API_KEY` pre-seeds. Modrinth needs no key.
- Monitoring: hybrid. Source order: (1) optional companion agent (future, `agent` field reserved in stats payload); (2) RCON (`list`, and `tick query` for MSPT when supported) + Docker stats (mem/cpu) + log stream. Stats payload below.
- i18n: English + Spanish. Theme: light/dark/system.
- Features also required: backups (scheduled, retention, restore, download), web file manager + text editor, scheduled tasks (cron: restart/command/backup) + crash auto-restart, Discord/generic webhooks, mod/plugin browser (CurseForge/Modrinth/Hangar-optional) + update check, player management (whitelist/ops/bans via RCON/files), audit log + personal API tokens (Bearer), server templates + clone, modpack export/import (CurseForge manifest zip, Modrinth .mrpack, server pack zip).

## Config (env)
`PORT` (8080), `DATABASE_URL`, `SECRET_KEY` (required, >=32 chars), `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `ADMIN_EMAIL`, `PUBLIC_URL` (e.g. https://craft.example.com; used for WebAuthn rpID/origin), `DATA_DIR` (/data; server data under `/data/servers/<id>`, backups `/data/backups/<id>`), `DOCKER_HOST`, `DOCKER_NETWORK` (servcrafty), `CURSEFORGE_API_KEY`, `HOST_DATA_DIR` (path of DATA_DIR as seen by the docker daemon; default = DATA_DIR, since dockerd runs in same container), `PORT_POOL_DEFAULT` ("25565-25600").

## WebSocket `/ws` (cookie auth). Client sends JSON:
`{type:"subscribe", serverId, channels:["logs","stats"]}` / `{type:"unsubscribe", serverId}` / `{type:"command", serverId, command}`

# Self-update feature (v0.2) – binding contract

Decisions (owner): GitHub Releases + semver tags (`vX.Y.Z`); stable releases only (GitHub `releases/latest` already excludes drafts/prereleases; also ignore any with `prerelease:true`); Docker install = **notify only** (show `docker compose pull && docker compose up -d`); LXC/source-checkout install = **Update button** in the UI; keep previous version for **rollback**; **warn if game servers are running** (they're separate containers and keep running; only the panel restarts for ~30s); **verify** the release: the tag's commit SHA from the GitHub API must equal `git rev-parse <tag>^{commit}` after fetching from the configured origin (which must be https://github.com/<UPDATE_REPO>.git), and surface GitHub's `verification.verified` for the tag/commit as `verified`.

Env: `UPDATE_REPO` (default `joaquincabrerasimoes/ServCrafty`), `UPDATE_CHECK` (default on; `0` disables network checks), `INSTALL_TYPE` (`docker` is set in the Dockerfile; `lxc` optional; if unset: app root has `.git` -> `lxc`, else `source`). Current version = `server/package.json` version (read at runtime); current commit from `git rev-parse HEAD` when available. GitHub calls unauthenticated with ETag + 6h cache (+ optional `GITHUB_TOKEN` env), 60 req/h limit respected; `checkError` reports failures; never crash on network errors.

## Apply mechanism (LXC/source)
The app must NOT update itself in-process (systemd kills the cgroup on restart). `POST apply` validates, then spawns the updater **outside the service cgroup**: `systemd-run --unit=servcrafty-updater --collect --no-block bash <copy-of lxc/apply-update.sh> <tag> <expectedSha> <appRoot> <dataDir>`; the script is first copied to `$DATA_DIR/update/apply-update.sh` (git checkout replaces the repo's copy mid-run). `apply-update.sh` (bash, set -Eeuo pipefail): lock file; write `$DATA_DIR/update/status.json` {state,step,targetVersion,fromVersion,startedAt,finishedAt,message} and append to `$DATA_DIR/update/update.log` at each step; steps: verify (origin url check, `git fetch --tags --force origin`, tag exists, `git rev-parse tag^{commit}` == expected sha, refuse if working tree dirty in tracked files); backup (record previous SHA/version into `$DATA_DIR/update/previous.json`, copy `server/dist` and `web/dist` to `$DATA_DIR/update/prev/`); checkout (`git checkout --detach <tag>`); install (`npm install --workspaces --include-workspace-root`); build (`npm run build --workspace web && npm run build --workspace server`); restart (`systemctl restart servcrafty`); health (poll `http://127.0.0.1:$PORT/api/health` up to 120s until ok AND reported `version` == target); on ANY failure after backup start: automatic rollback (checkout previous SHA, restore dist from prev/, `npm install`, restart, wait healthy) and state `rolled_back` with message. Success -> state `succeeded`. Manual rollback uses the same code path (`apply-update.sh --rollback`). Note DB migrations are forward-only and additive; mention in UI/docs that a rollback does not revert DB migrations.
`GET /api/health` additionally returns `version`.

## REST (admin only; audit-logged `update.check|update.apply|update.rollback`)
- `GET /api/admin/update` -> `{ currentVersion, commit: string|null, installType: "lxc"|"docker"|"source", canUpdate: boolean, cannotUpdateReason: string|null, checkedAt: ISO|null, checkError: string|null, updateAvailable: boolean, latest: null | { version, tag, name, notes (markdown), url, publishedAt, commitSha, verified: boolean }, dockerCommand: string|null, runningServers: number, status: { state: "idle"|"running"|"succeeded"|"failed"|"rolled_back", step: string|null, fromVersion: string|null, targetVersion: string|null, startedAt: ISO|null, finishedAt: ISO|null, message: string|null }, rollbackAvailable: boolean, previousVersion: string|null }` (cached; reads status.json).
- `POST /api/admin/update/check` -> same payload after a forced fresh check (rate limited).
- `POST /api/admin/update/apply` body `{ version?: string }` -> `202` same payload. Errors: `409 update_in_progress`, `400 cannot_update` (installType != lxc/source-with-systemd, missing git/systemd-run), `400 no_update`.
- `POST /api/admin/update/rollback` -> `202`; `400 no_rollback`.
- `GET /api/admin/update/log?offset=N` -> `{ text, offset, state }` (tail of update.log from byte offset).
`canUpdate` requires: installType lxc|source, `git` repo present, `systemd-run` + `systemctl` available, running as root, app root writable.

## CI (GitHub Actions) `.github/workflows/release.yml`
On push of tag `v*.*.*`: verify tag == `server/package.json` version (fail otherwise); build & push `ghcr.io/<owner>/servcrafty:<version>` and `:latest` (docker/build-push-action, linux/amd64, `permissions: packages: write, contents: write`); create the GitHub Release with auto-generated notes (`gh release create --generate-notes --verify-tag`, mark as prerelease if the tag has a `-` suffix like `v1.0.0-rc.1`). Also a `scripts/release.sh <patch|minor|major|X.Y.Z>` that bumps versions in root/server/web package.json, commits "Release vX.Y.Z", tags, and prints the push command (does not push).

## Frontend
Admin-only: (1) a dismissible banner in the main layout when `updateAvailable` ("ServCrafty vX is available – you're on vY"; link to the Updates page; dismissal remembered per version in localStorage; check on mount and every 30 min); (2) page `/admin/update` ("Updates", in the admin nav) with current/latest versions, install type, release notes (render markdown safely: headings, lists, links, code; no raw HTML), `verified` badge, "Check now", and: for `lxc/source` an **Update to vX** button with a confirm dialog that shows the warning "the panel restarts for about 30 s; N game server(s) are running and will keep running" (when runningServers>0), then a live progress view (poll `GET /admin/update` + `/log` every 2 s, tolerate the API being down during restart, reload the page when the new version reports healthy), result states succeeded/failed/rolled_back with message, and a **Rollback to previous version** button when `rollbackAvailable`; for `docker` show the command from `dockerCommand` with a copy button and no update button; when `!canUpdate` show `cannotUpdateReason`. Current version shown in the sidebar/footer and on the System page. i18n en + es. 

## Host-wide limits (v0.1.3)
- Admin setting `globalLimits` `{maxServers,maxRamMb,maxCpu,maxDiskMb}` (null = no cap), in `GET/PUT /api/admin/settings` (also returns `hostUsage`). Caps apply to ALL users' servers combined and also bind admins; checked on create and on edits that grow a resource (400 `host_capacity_exceeded`). With a disk cap set, a server needs a disk limit.
- `GET /api/account/quota` adds `host: {limits, usage}`; the UI shows each user's effective limit = min(own quota, what the host still has free), and `∞` only when neither exists.
- `GET /api/servers/:id/join-attempts`, `DELETE /api/servers/:id/join-attempts/:name`: players refused by the whitelist (Java, parsed from the log).

## Other games: Terraria (v0.2.0)
Binding contract for the multi-game work. Every existing Minecraft behaviour must stay exactly as it is.

**Model.** `servers.game` (`'minecraft'` default | `'terraria'`) says which game a server runs; `servers.type` stays the variant. New types: `TERRARIA` (vanilla), `TSHOCK`, `TMODLOADER`. New JSONB column `servers.terraria` (null for Minecraft). `game` is derived from `type` by one helper (`gameOf(type)`), never trusted from the client; API JSON exposes `game` and `terraria` on every server. Migration `007_terraria.sql` adds the columns and widens the `type` check (existing constraint name `servers_type_check`).

**Images (all `linux/amd64`, pulled on first start like the Minecraft images).**
| type | image | notes |
|---|---|---|
| TERRARIA | `hexlo/terraria-server-docker:latest` | env-driven (lower-case vars), worlds at `/root/.local/share/Terraria/Worlds`, container port 7777/tcp, needs `tty`+`stdin_open`; console = write `<cmd>
` to the attached stdin (no leading slash); graceful stop = command `exit` (saves) then stop |
| TSHOCK | `ghcr.io/pryaxis/tshock:latest` | configured by command-line args (`-world /worlds/<file> -autocreate N -worldname .. -seed .. -difficulty N -maxplayers N -password .. -motd ..`), mounts `/tshock` (config, logs), `/worlds`, `/plugins`, ports 7777 (REST 7878 is NOT published), `tty`+`stdin_open`; console via stdin, stop via `exit` |
| TMODLOADER | `jacobsmile/tmodloader1.4:latest` | env `TMOD_*` (`TMOD_AUTODOWNLOAD`/`TMOD_ENABLEDMODS` = comma-separated Workshop IDs, `TMOD_PASS`, `TMOD_WORLDNAME`, `TMOD_WORLDSIZE`, `TMOD_WORLDSEED`, `TMOD_DIFFICULTY`, `TMOD_MAXPLAYERS`, `TMOD_MOTD`, `TMOD_SECURE`, `TMOD_LANGUAGE`, `TMOD_UPNP=0`), data dir `/data` (worlds in `/data/tModLoader/Worlds`), console via `docker exec <container> inject "<cmd>"`, graceful stop via `inject "exit"` |
`SERVCRAFTY_IMAGE_TAG` (existing env override) also selects the tag for these images. The image name/tag table lives in ONE place (`server/src/lib/games.ts`).

**Terraria config** (`TerrariaConfig`, zod-strict, `server/src/lib/terrariaConfig.ts`, camelCase):
`worldName` (1-32 chars `[A-Za-z0-9 _-]`, default "ServCrafty"), `size` 1|2|3 (default 2), `difficulty` 0|1|2|3 (normal/expert/master/journey, default 0), `seed` (optional, <=40 chars `[A-Za-z0-9 _-]`), `maxPlayers` 1-255 (default 8), `password` (optional, <=64 chars, no quotes/backslashes/control chars), `motd` (optional, <=100 chars, no control chars), `secure` bool (default true), `language` (optional, one of en-US de-DE it-IT fr-FR es-ES ru-RU zh-Hans pt-BR pl-PL), `workshopMods` (TMODLOADER only; array of numeric Workshop id strings, max 200; others -> 400). `world` creation values (size/difficulty/seed/worldName) matter only while the world file does not exist (autocreate); password/maxPlayers/motd/secure/language/mods are applied on every start. Invalid -> 400 `invalid_terraria_config`. A server of game `terraria` rejects `minecraft`, `mcVersion` other than `LATEST`, `modpack`, `lanAnnounce`, `javaArgs`; a Minecraft server rejects `terraria`.

**HTTP additions.**
- `POST /servers` and `PATCH /servers/:id` accept `terraria` (PATCH merges and validates the whole object); `type` selects the variant. Terraria servers: `memoryMb` min 512, port mapped to container 7777/tcp.
- `GET /servers/:id/terraria/worlds` -> `[{ name, sizeBytes, modifiedAt }]` (`.wld` files in the server's Worlds dir).
- `POST /servers/:id/terraria/world` (multipart, one `.wld` and optionally its `.twld` companion; max 256 MB; manager level; server must be stopped; refuses to overwrite an existing world of the same name unless `?overwrite=1`) -> `{ worldName }`; the server then starts with `worldFile`/world name set to that file (the route also sets `terraria.worldFile`).
- Players for Terraria: `GET /servers/:id/players` and `Stats.players.list` come from the log (`<name> has joined.` / `<name> has left.`, see `runtime.ts`), `POST /servers/:id/players/:name/{kick|ban|pardon}` run `kick`/`ban` console commands; `pardon` edits `banlist.txt`; `op`, `deop`, `whitelist-*` -> 400 `unsupported`. `GET /servers/:id/lists/banned` reads `banlist.txt` (names and IPs, one per line, as `{name}`); `ops` and `whitelist` return `[]`.
- Everything Minecraft-specific answers 400 `unsupported_game` for a Terraria server: properties, mods/plugins catalog install, modpack export, LAN announce. Console commands, power, backups (a `save` command is sent first), schedules, webhooks, sharing, files, stats, logs, clone, delete work for both games.
- Stats for Terraria: `tps`/`mspt` null, `players` from the log, `source: 'docker'`, `version` from the log banner (`Terraria Server v1.4.4.9`) when seen, memory/cpu from docker stats.

## SteamCMD games (v0.3.0)
Binding contract. Every existing Minecraft/Terraria behaviour stays exactly as it is. One generic implementation runs ANY SteamCMD game from a **game definition** (JSON metadata). Rules: the main port is the one with `"main": true` (default: the first); it is the one shown in the UI, used for copy-address and stored in `servers.port`. `publish:false` ports are NOT published on the host (only reachable by the panel proxy over the docker network). `mirror:true` means the container port equals the host port allocated from the pool (needed when the game advertises its port to the Steam browser); `{{ports.<id>}}` always renders the container-side port number. `offset: {from, by}` (by 1-100) makes a port's host port exactly the host port of `from` plus `by` (e.g. KF1 GameSpy = game + 1): `from` must be an existing published port without an offset of its own (no chains/cycles), the offset port must be published and may not be the main port, its protocol may differ, two offset ports may not share the same `from`+`by`, and with `mirror:true` its container port is that host port. Allocation picks, in pool order, the first base port for which every dependent `base + by` is also free and inside the pool (409 `no_free_ports` when no block fits); host ports always come from the pool. A published port with `protocol:"both"` is bound for tcp and udp. Variables: `type:"password"` values are secret (blanked for viewers/operators, never logged; the plan file is mode 0600). Template syntax: `{{key}}` variable (after `valueMap`), `{{ports.<id>}}`, `{{server.name}}`, `{{server.id}}`, `{{workshop.ids}}` (comma separated); no code, no filters; an unknown name is a definition validation error. `launch.command` is an argv ARRAY (never a shell string); an element object with `if` is included only when that variable is truthy (non-empty and not `false`/`0`). A composite element `{parts, separator, if?}` renders its non-skipped parts (plain strings, or `{value, if?}` skipped when `if` is falsy) joined by `separator` (default empty); it is omitted when its own `if` is falsy or every part is skipped; `parts` needs at least one entry; the first element must be a plain string. A `string`/`password` variable may set `generate: {length 8-64 (default 20), charset "alnum"|"hex" (default "alnum")}`: when a server is created (POST /servers, template instantiate, clone) with the value absent or empty, the panel generates it with `crypto.randomBytes` (unbiased mapping) and stores it; `required` is then never violated by emptiness and a non-empty client value is kept; `generate` cannot be combined with `default` or `pattern`, and `length` must fit `min`/`max`. Generated variables are secret like passwords. `POST /servers/:id/steam/regenerate {key}` (manager, audit `server.steam_regenerate`) sets a new value (applied on next start) and returns `{key, value, restartRequired}`; PATCH with an empty/null value for such a variable regenerates it. File paths are relative to the game install dir (`/data/game`) and may not contain `..`.

**Web UI proxy.** For each `webui` entry the panel serves `ALL /api/servers/:id/webui/:uiId/*` as an authenticated reverse proxy to `http://<container ip>:<containerPort><path>` over the `servcrafty` network (HTTP/1.1; WebSocket only for entries with `"websocket": true`, see below). Requires the entry's `minAccess` (default manager). With `auth.type:"basic"` the panel injects the `Authorization` header. With `rewrite:true`, text responses (html/css/js) get root-absolute URLs (`href="/..."`, `src="/..."`, `action="/..."`, `url(/...)`, string literals starting with `/`) prefixed with `/api/servers/:id/webui/:uiId`; `Location` redirects and `Set-Cookie` paths are rewritten; upstream `X-Frame-Options`/CSP `frame-ancestors` are removed and replaced by `frame-ancestors 'self'`. 502 `webui_unreachable` when the server is not running. It only ever connects to that container's declared port (SSRF-safe); upstream timeout 30 s; response size capped.

**Web UI WebSockets.** Entries with `"websocket": true` (default false) accept WebSocket upgrades, only on the token URL (`.../webui/:uiId/~t/<token>/<path>`; clients cannot follow the entry redirect -> 400 `webui_session_required`). At the upgrade the token and the user's access (`minAccess`) are re-checked like HTTP; the browser `Origin` must be absent, `null` (the sandboxed page) or the panel's own origin (else 403 `origin_not_allowed`); the path is normalised (dot segments, also encoded, refused). The panel first opens `ws://<container ip>:<containerPort><path>` (Origin `http://<ip>:<port>`, the definition's basic auth, the session's upstream cookies; never the browser's Cookie/Authorization/Origin; the client's subprotocols offered and the upstream's choice returned to the client), then bridges text/binary frames and pings both ways with close codes propagated. Limits: 1 MiB per message, 4 MiB queued before the sending side is paused (backpressure), 10 min idle timeout, 20 sockets per server and user (429 `too_many_websockets`); upstream down -> 502 `webui_unreachable` (or close 1011 once bridged). Every proxied socket of a server is closed (1001) when it stops, restarts or crashes. Text rewriting also covers absolute `http(s)://`/`ws(s)://<upstream ip:port>` URLs (rewritten to the panel host + proxy prefix) and `${location.host}/...` / `location.host + "/..."` constructions.

**Implementation notes / deviations (backend, v0.3.0).**
- Web UI proxy hardening: proxied pages are served with `Content-Security-Policy: sandbox allow-scripts allow-forms allow-popups allow-modals allow-downloads; frame-ancestors 'self'` (opaque origin), so a game's web UI can never act with the viewer's panel session. Because a sandboxed frame does not send the panel cookie, `/api/servers/:id/webui/:uiId[/<path>]` (cookie auth, GET/HEAD) answers 302 to `/api/servers/:id/webui/:uiId/~t/<token>/<path>` (bare base or `/` -> the entry's `path`); the token is random, bound to user+server+UI, idle 2 h / max 12 h, access re-checked on every request. Rewriting therefore prefixes root-absolute URLs with `.../webui/:uiId/~t/<token>`. Browser `Cookie`/`Authorization` are never forwarded; upstream `Set-Cookie` is kept in a per-token jar on the panel (not path-rewritten to the browser). Only an allowlist of request headers is forwarded; `Origin` is rewritten to the upstream. Response cap 32 MB, request body cap 16 MB, 30 s overall timeout. The iframe/new-tab URL is in server JSON `steamGame.webui[].url`.
- `GET /games` items are the full definition minus `scripts` (web UI `auth` reduced to `{type}`), plus `builtin`, `hasWorkshop`, `hasWebui`, `hasConsole`, `hasPlayers`; ports carry a resolved `main` flag. SteamCMD servers never take a client `port`: POST with `port` or PATCH changing it -> 400 `port_not_supported` (clone ignores it).
- Server JSON adds `steamGame` (`{id,name,icon,builtin,hasWorkshop,hasWebui,hasConsole,hasPlayers,ports:[{id,label,protocol,hostPort|null,main}],webui:[{id,label,minAccess,url}]}`, webui filtered by the viewer's access).
- The plan file lives at `$DATA_DIR/steam-plans/<serverId>.json` (0600, dir 0700), outside the server dir so it is neither a user file nor part of backups.
- `POST /servers/:id/workshop/refresh` sets an internal `steam.workshopRefresh` flag; the next start deletes `/data/workshop` before creating the container (forcing re-download). `validateNext`/`workshopRefresh` are cleared once a start has consumed them. Workshop mutations return `{workshop, restartRequired}` (add also `item`); `GET /workshop/items/:id` accepts `?gameId=` and returns `matchesGame`.
- Definition rules beyond the schema text: variable `pattern` must match the whole value (implicitly anchored); number variables may set `integer: true`; `min`/`max` on string/password are lengths; port ids `^[a-z][a-z0-9_-]{0,31}$`, variable keys `^[A-Za-z][A-Za-z0-9_]{0,47}$` (`ports`, `server`, `workshop` reserved), web UI ids `^[a-z][a-z0-9-]{0,31}$`; the main port and mirror ports must be published; the A2S port must be udp/both, web UI ports tcp/both; `launch.cwd`, file paths and `workshop.dir` take no templates; `workshop.dir` is required for `install:"steamcmd"`; `stop.type:"stdin"` requires `stop.command` and `console.stdin:true`; player regexes need `(?<name>...)`; the first `launch.command` element must be a plain string. Variable values containing control characters (line breaks) are rejected.
- Non-admin authors (`can_author_games`) may only update/delete their own custom definitions (a definition's scripts run in every server that uses it); admins may change any custom definition. `can_author_games` is exposed raw as `canAuthorGames` (admins can author regardless).
- `eula` is not required for `type:"STEAMCMD"` (POST /servers and template instantiate). The per-server `env` is not passed to SteamCMD containers (only `SERVCRAFTY_IMAGE_TAG` is honoured, for the image tag); the game environment comes from `launch.env`.
- Clone of a SteamCMD server copies its configuration only (`copyFiles` is ignored); shared templates drop `password` variables. Player actions (`/players/:name/*`) answer 400 `unsupported` for SteamCMD servers and `lists/*` return `[]`. Console commands on a definition without `console.stdin` answer 400 `console_unsupported`.
- On start, published ports the definition gained after creation are allocated (and stale ones dropped); a missing allocation answers 409 `port_not_allocated`, a mirror port colliding with another container port 409 `port_conflict`. Ports used by `extra_ports` count as taken for every game's allocation and for the admin port-pool check/`GET /admin/ports`.
- Port offsets (approved addition): on start, a server created before its definition gained an offset keeps its ports when they already satisfy the offsets; a wrong/missing offset port is set to `base + by` when that number is free; otherwise the whole group (base included, possibly the main port) is re-allocated, which happens only while the server is stopped and is written to the server log (a PATCH on a running server never moves ports). `GET /games` and `steamGame.ports` carry each port's `offset`.
- Composite launch arguments and generated secrets (approved additions, see Rules). Clone and template save never copy generated values (fresh ones are generated on creation); shared templates also keep dropping password values. A stored config whose definition later gained `generate` gets the missing value generated and stored at the next start (logged). Unknown `generate` variable in regenerate -> 400 `not_generated`.
- Web UI WebSockets (approved addition, see "Web UI WebSockets"). The panel's shared WebSocket server now allows 1 MiB messages; `/ws` keeps its own 64 KiB limit (close 1009).
- Restoring a SteamCMD backup that does not contain `game/`, `workshop/` or `steam/` keeps the current copies of those directories. `STEAM_API_KEY` env is a fallback for the admin setting.

- Setting `disabled_games` = `{ "<gameKey>": { "blockStart": boolean, "disabledAt": iso, "by": userId } }` (key absent = enabled). A disabled game cannot be used to CREATE servers by anyone (admins included): 409 `game_disabled`. Existing servers: with `blockStart:false` they run and start normally; with `blockStart:true` they cannot be started (`start`, restart, auto-start, schedules and the Steam update action answer 409 `game_disabled`) and running ones were stopped gracefully when the flag was set.
- API (admin only): `GET /admin/games` -> `[{key, name, builtin, kind:'minecraft'|'terraria'|'steam', disabled, blockStart, servers, running}]` (all three kinds, so Minecraft and Terraria are listed too); `PUT /admin/games/:key/disabled` `{disabled: boolean, blockStart?: boolean}` (`:key` is URL-encoded, e.g. `steam%3Asatisfactory`; `blockStart` defaults false; enabling clears everything); response `{key, disabled, blockStart, stopped: n}` where `stopped` = servers stopped by the call; when `blockStart` is true all running servers of that game are stopped gracefully (system stop, not counted as a user stop, so auto-start semantics are unchanged once re-enabled) and an audit entry `game.disable` / `game.enable` (with counts) is written. Setting `blockStart` later on an already disabled game is allowed (same endpoint). `GET /games` items gain `disabled` and `blockStart`; server JSON gains `gameDisabled: boolean` and `gameBlocked: boolean` (= blockStart) so the UI can show a banner and disable Start.
- Deleting a custom definition that is disabled works as before (still 409 while servers use it).

**4. Process monitor (admin only).**
- `GET /admin/processes` -> `{ takenAt, intervalMs, host: {cpuCount, memTotalMb}, servers: [{ serverId, name, game, gameKey, status, containerId, cpuPercent, memUsedMb, memLimitMb, processes: [{ pid, ppid, user, cpuPercent, memMb, memPercent, state, elapsedSec, cpuTimeSec, command }] }], dockerAvailable }`. Only RUNNING game containers (label-selected / from the DB), only processes inside them (NOT the panel's own process or other host processes). Source: Docker `top` (`ps` args `-eo pid,ppid,user,time,rss,stat,etime,args`; runs against the container PIDs so no tools are needed inside the image). Per-process `cpuPercent` is instantaneous like htop: computed from the delta of cumulative `cpuTimeSec` between two samples kept in memory per container and pid (first sample falls back to lifetime average `cpuTime/elapsed`); `memPercent` = rss / host or container memory limit. Container-level `cpuPercent`/`memUsedMb`/`memLimitMb` come from the same stats the runtime already has (no extra docker stats call). The response is cached for ~1.5 s so several viewers do not multiply docker calls; at most ~64 servers; commands are truncated to 500 chars and the result never contains environment variables or any `scf_`/password-like arguments (redact `--password`, `-password`, `+password`, `rcon_password`, `-ServerPassword`, anything following those flags, and `scf_...` tokens).
- Read-only: no kill/signal endpoint.
- UI: `/admin/system` gets a **Processes** section styled like htop: a header with per-server CPU and memory bars (container totals and the host core count), then a dense monospace table (PID, USER, CPU%, MEM (RSS), MEM%, STATE, TIME, COMMAND) with colour-coded CPU/MEM cells, grouped under a header row per server (collapsible; name, game, status, totals) with a "flat list" toggle, click-to-sort on any column (default CPU% desc), text filter, server filter, refresh interval selector (1 s / 2 s / 5 s / paused, default 2 s, auto-paused when the tab is hidden), a "not running" empty state and a docker-unavailable state; usable at phone width (horizontal scroll of the table, header stays readable).

**UI summary.** Admin > Users: a "Games" action per user (dialog with a checklist of every game key: Minecraft, Terraria, each Steam game; select all / none; shows the count granted; admin users are labelled "unrestricted"; the users table shows a compact summary such as "3 games" or "none"). Admin > Games: all games listed (Minecraft and Terraria as built-in rows, no edit, only the toggle) with an Enabled switch; turning one off opens a confirm dialog that shows how many servers exist/are running and asks "Also stop the running servers and prevent existing servers from starting?" with the choices "Only block new servers" (default) and "Also stop and block starting" (danger styling); disabled rows get a badge. Create wizard: only `creatableGames` are selectable; disabled-by-admin cards are shown greyed with a note; if the user has none: an empty state "An administrator has not enabled any game for you". Server pages: when `gameBlocked` the Start/Restart controls are disabled with an explanation and a banner; when only `gameDisabled` a quiet notice. Account > API tokens: the documentation button. i18n en + es for everything.

**Implementation notes / deviations (v0.3.2 backend).**
- One enforcement point: every creation path (POST /servers, clone, template instantiate, the three import kinds, and a server pack whose `servcrafty.json` names another game) goes through `createServer`, which checks the game key BEFORE any other validation or database work: 409 `game_disabled` first (everyone), then 403 `game_not_allowed` (non-admins). The allowlist checked is the CREATING user's; an admin creating a server for another user (`ownerId`) is unrestricted. Pure decisions in `lib/gameAccess.ts`, data access in `services/gameAccess.ts`, admin game control in `services/gameControl.ts`, routes in `routes/adminGames.ts`.
- `user_game_access.game_key` has a CHECK constraint on the key format. `PUT /users/:id/games` returns the same shape as GET; on an admin user the list is still stored (it applies if the user is demoted) and the response is `{games:null, unrestricted:true}`. Unknown keys -> 400 `unknown_game` with `details.unknown`. The stored list is de-duplicated and returned in canonical order (minecraft, terraria, definitions by name). User JSON from POST/PATCH /users also carries `allowedGames`; `creatableGames` is in the login/MFA responses, `GET /auth/me` and `PATCH /account`.
- `PUT /admin/games/:key/disabled` on a key that is neither an existing game nor currently disabled -> 404 `unknown_game`. Re-disabling keeps the original `disabledAt` (`by` = latest admin). The audit meta is `{blockStart, servers, stopped, failed?}`. The call waits for the graceful stops (in parallel, the same `stop(id, false, manual=false)` path as host shutdown via `runtime.systemStopServers`), so it can take up to a game's stop timeout. Servers in `running|starting|installing` are stopped.
- blockStart is enforced inside `runtime.start` (covers manual start, auto-start at boot, crash auto-restart, scheduled start, backup restore restart) and `runtime.restart` checks before stopping (a blocked server is never left stopped by a restart). `POST /servers/:id/power` (start/restart) and `POST /servers/:id/steam/update` check synchronously so the client gets 409 `game_disabled` (start/restart otherwise run in the background). Schedules record the 409 as their `lastError`.
- Deleting a custom definition also forgets its grants and its `disabled_games` entry (a new definition may reuse the id).
- `gameDisabled`/`gameBlocked` in server JSON come from an in-memory snapshot of the setting, loaded at boot and refreshed on every check/change.
- Process monitor: lists servers whose runtime status is `running|starting|installing|stopping` with a container (sorted by name, max 64). Each server item also has `cpuLimit` (cores allotted); the container `cpuPercent` is the runtime Stats value (percent of the allotment), while process `cpuPercent` is per core like htop (100 = one core). Because `ps` times have a 1 s resolution, the CPU baseline is the OLDEST sample of the pid from the last 10 s (up to 6 kept per pid), which smooths the quantisation; a pid whose CPU time goes backwards is treated as a new process. Containers not sampled for 60 s (or no longer listed) and dead pids are dropped; at most 20,000 pids are tracked. A container that vanishes mid-request is listed with `processes: []`; Docker down -> `dockerAvailable:false` and empty process lists. `parseTop` accepts procps and BusyBox output (`mm:ss` with minutes > 59, RSS with `k/m/g` suffixes). Redaction: `scf_...` tokens, `name=value`/`name:value` pairs whose name contains pass/password/passwd/secret/token/api-key/auth-key (also inside `?a=b` game URLs), and the argument after a flag with such a name (`--password x`, `+rcon_password x`, `-ServerPassword x`); control characters become spaces; truncated to 500 chars.
- `docker top` runs `ps` inside the daemon's environment: the Docker image's dockerd is in the Alpine panel container, whose `ps` is BusyBox unless `procps` is installed there.

## BlueMap (v0.4.0)
A live 3D map of Java servers (BlueMap), stored in the panel's PostgreSQL database and viewed through the panel's proxy.

- **Servers.** `bluemapKind(type)`: `plugin` for PAPER, PURPUR, FOLIA, SPIGOT (config in `plugins/BlueMap/`), `mod` for FABRIC, QUILT, FORGE, NEOFORGE (config in `config/bluemap/`). Vanilla, Bukkit, CurseForge/Modrinth modpacks, Bedrock, Terraria and SteamCMD servers are unsupported (400 `bluemap_unsupported`).
- **Storage.** Migration `011_bluemap.sql`: `servers.bluemap jsonb` = `{enabled, schema, role, passwordEnc, enabledAt}` (`passwordEnc` encrypted with SECRET_KEY). Each server that enables BlueMap gets, in the panel's own database, a schema and a login role both named `bluemap_<server uuid without dashes>`. The schema is owned by the panel's database user; the role (NOSUPERUSER NOCREATEDB NOCREATEROLE, CONNECTION LIMIT 20, `search_path` = its schema) only has USAGE and CREATE on its schema, so a plugin on that server cannot read ServCrafty's own tables or another server's map. The panel's database user needs CREATEROLE and CREATE on the database (400 `bluemap_db_privileges` otherwise). Enabling verifies that the new role can log in (502 `bluemap_db_login_failed`) and undoes what it created if anything fails. Identifiers are validated against `^bluemap_[0-9a-f]{32}$` and never come from user input.
- **Database address for containers.** Host and port come from `DATABASE_URL`, or from the admin setting `bluemap_db_host` (`host` or `host:port`, Admin > Settings, `bluemapDbHost` in `/admin/settings`). A loopback host (localhost, 127.x, ::1) cannot be reached from containers: enabling answers 400 `bluemap_db_unreachable`. `sslmode` of `DATABASE_URL` is forwarded to the JDBC URL (`jdbc:postgresql://host:port/db?currentSchema=<schema>`).
- **Install.** itzg installs BlueMap from Modrinth: `MODRINTH_PROJECTS` gets `bluemap` added once (the admin's own entries stay) and `MODRINTH_DOWNLOAD_DEPENDENCIES=required` is defaulted. Before each start (`prepareBluemap`) the panel writes `core.conf` (accept-download true, metrics off), `webserver.conf` (port 8100, `sse-enabled: false` because the proxy cannot carry event streams; the webapp falls back to polling) and `storages/sql.conf` plus an identical `storages/file.conf` (credentials; always rewritten; BlueMap generates its default maps with `storage: "file"` and aborts loading when no storage of that name exists, so `file` is defined as the same PostgreSQL storage) under the config directory, and switches BlueMap's generated map configs from `storage: "file"` to `"sql"`. BlueMap writes those map configs itself on its first run, so a watcher (`watchBluemapMaps`) polls every 10 s for up to 15 minutes after the start, patches new ones, and sends `bluemap reload` once the server is `running`. Files with the first line `# servcrafty-managed: BlueMap` are the panel's; a file without it that exists is never overwritten (except `sql.conf`).
- **Enabling needs consent.** `acceptDownload: true` (Mojang EULA: BlueMap downloads the Minecraft client) or 400 `bluemap_eula_required`.
- **Disabling / cleanup.** Disabling keeps the role, schema and stored map (re-enabling reuses them). At the next start of a server that does not have BlueMap enabled, the panel removes the managed config files and BlueMap's jar (`bluemap.jar` / `bluemap-<version>-<loader>.jar` in `plugins/` or `mods/`) when it finds a managed file, so a clone, template instance or restored backup of a BlueMap server can never keep writing into the original's schema. A BlueMap the user installed and configured by hand (no marker) is not touched.
- **Deleting a server** drops its schema (CASCADE) and role first, freeing the space; if the drop fails the server is still deleted and the schema name is logged. `deleteData` on disable and `reset` drop/recreate the schema and need the server stopped (409 `server_running`).
- **API.** `GET /servers/:id/bluemap` (viewer) -> `{supported, enabled, kind, dataBytes, tables, dbIssue, restartRequired, url}`; `PUT /servers/:id/bluemap` (manager) `{enabled, acceptDownload?, deleteData?}` -> same shape, audit `server.bluemap_enable|bluemap_disable`; `POST /servers/:id/bluemap/reset` (manager, stopped) -> audit `server.bluemap_reset`. Server JSON gains `bluemap: {supported, enabled, url}`.
- **Viewing.** The built-in web UI id `bluemap` of the web UI proxy (`/api/servers/:id/webui/bluemap/`, viewer access, container port 8100, no rewriting, no WebSocket). The proxy adds `Access-Control-Allow-Origin: *` to proxied responses (the sandboxed page has an opaque origin, so its module scripts and fetches need CORS; the URL carries the secret proxy token and no credentials are involved), and injects an in-memory `localStorage`/`sessionStorage` stand-in into BlueMap's HTML (storage access throws in a sandboxed frame).
- **UI.** Server tab **Map** (managers always, viewers once enabled): enable card with the Mojang EULA checkbox and the `dbIssue` warning, then the proxied map in an iframe (retries while BlueMap starts), plus stored size and *Turn off* / *Delete map data* / *Render again*. Admin > Settings: *BlueMap database address*. i18n en + es.

## BlueMap JDBC driver and other Minecraft versions (v0.4.2)
- BlueMap ships no PostgreSQL driver. Before each start `prepareBluemap` copies `postgresql-42.7.4.jar` (downloaded once from Maven Central, SHA-1 checked, cached in `<data>/cache/bluemap/`) into the BlueMap config directory and `storages/sql.conf` / `file.conf` set `driver-jar` (`/data/<config dir>/postgresql-42.7.4.jar`) and `driver-class: org.postgresql.Driver`. A failed download answers 502 `bluemap_driver_download`. The jar is removed with the other managed files when BlueMap is off.
- Create wizard: a switch under the version picker (Vanilla, Paper, Folia, Fabric, Quilt) calls `GET /catalog/minecraft/versions?snapshots=true`, which also lists snapshots, pre-releases, release candidates and (Vanilla) old betas/alphas. "Latest" still means the newest release.

## Server icon (v0.4.4)
- Minecraft Java servers (not Bedrock) can have a multiplayer-list icon: `server-icon.png` in the server's data directory, a PNG of exactly 64x64 pixels. The panel reads and writes that file, so one placed through the file manager works too.
- `GET /servers/:id/icon` (viewer) returns the PNG (404 without one); `PUT /servers/:id/icon` (manager, multipart `file`) validates PNG signature, 64x64 and at most 256 KB (400 `invalid_icon`), audit `server.icon_set`; `DELETE` removes it, audit `server.icon_removed`. Both answer `{icon, restartRequired}`: Minecraft reads the icon when the server starts.
- Server JSON gains `icon`: the file's mtime in ms or null, used as `?v=` for cache busting.
- UI: Settings page card "Server icon" (any image is centre-cropped and scaled to 64x64 in the browser, with preview, then saved), and the icon is shown on the dashboard rows. Viewers see the card only when an icon exists.

## BlueMap public link (v0.4.5)
The owner of a server (or an admin) can publish the live BlueMap so that anyone with the URL can view it **without signing in**.

- **Link.** `.../api/servers/<id>/webui/bluemap/~t/<token>/` (same shape as a proxy session URL). The token is 24 random bytes (base64url), stored encrypted with SECRET_KEY in `servers.bluemap.publicTokenEnc`, so the owner can read the link again. The URL fragment (`#world:x:y:z...`) stays in the browser, so a link can point at a map position.
- **API.** `PUT /servers/:id/bluemap/public` `{enabled, regenerate?}` (owner/admin only, BlueMap must be on) returns the BlueMap status, whose `publicEnabled` is visible to every viewer but whose `publicUrl` (a secret) is only given to the owner/admin. Audit `server.bluemap_public_enable|regenerate|disable`.
- **Revoking.** Turning the link off, regenerating it, or turning BlueMap off (or deleting its data) cancels the old URL. Checks are cached for 5 seconds, so a revoked link may work for a few more seconds.
- **What a visitor can do.** Only `GET`/`HEAD` of the BlueMap page of that one server (405 otherwise); nothing else of the panel, no API, no other web UI. The visitor gets a throw-away proxy session (own empty cookie jar). At most 24 upstream requests per server are in flight for public visitors (429 beyond), so anonymous traffic cannot starve the game server. Public requests are not subject to LAN-only restrictions: that is the point of the link.
- **Privacy.** The live map shows where online players are. The UI warns about this.
- **UI.** Map tab, card "Public link" for the owner/admin: create, copy, regenerate, turn off.

## BlueMap markers and multiple public links (v0.4.6)
**Markers.** The BlueMap API (`MarkerSet`, POI/HTML/Line/Shape/Extrude markers) does not persist markers, so ServCrafty stores them in its own database (`bluemap_marker_sets`, `bluemap_markers`, migration 012) and serves them to the web map itself: the proxy answers `maps/<id>/live/markers.json` by merging our sets (ids prefixed `sc-`) into whatever BlueMap serves. No Java addon is needed, and it works with every BlueMap version. Types: `poi` (pin + popup), `html` (text label), `line`, `shape` (polygon at `y`), `extrude` (polygon between `minY`/`maxY`). Free text is plain text and always HTML-escaped on output. Limits: 2000 markers and 50 sets per server, 200 points per line/shape.
- **REST** (API tokens work): `GET/POST /servers/:id/bluemap/markers`, `PATCH/DELETE .../markers/:markerId`, `GET/POST .../marker-sets`, `PATCH/DELETE .../marker-sets/:setId`. Read = viewer, markers/new sets = operator, change/delete a set = manager. A marker needs `setId`, or `mapId` for the map's default set (created on first use). Audit `server.bluemap_marker_*`, `server.bluemap_set_*`.
- **Refresh.** BlueMap polls markers every 10 s, but stops polling when its live event stream connects, which never carries our markers; the injected script therefore refreshes them every 15 s.
**Public links (replaces the single link of v0.4.5).** Table `bluemap_public_links` (the v0.4.5 link is migrated to a row named "Public link"). Owner/admin: `GET/POST /servers/:id/bluemap/links`, `PATCH/DELETE .../links/:linkId` (`name`, `canEdit`, `regenerate`); up to 20. `canEdit` is chosen at creation and can be changed. All links stop when BlueMap is turned off. `PUT .../bluemap/public` is gone; `BluemapStatus.publicEnabled/publicUrl` became `publicLinks` (count).
- **Edit links.** A link with `canEdit` lets visitors create markers and change/delete **only the markers created through that same link** (`created_by = link:<id>`); panel users with operator access change any marker. Visitors still only read the map itself (GET/HEAD).
**Map page editor.** The proxy injects a script into the BlueMap page (`lib/bluemapEditor.ts`) for everyone with the map (viewers only get the refresh), and the editor UI when the viewer may edit. It talks to the panel under the token URL: `GET __servcrafty/markers?mapId=`, `POST __servcrafty/markers` (create), `POST __servcrafty/markers/<id>` (change), `POST __servcrafty/markers/<id>/delete`; only GET/POST, `text/plain` bodies, so the sandboxed page needs no CORS preflight. Landscape: side panel. Portrait: bottom sheet. "Add marker here" collapses the sheet to a bar with a crosshair at the screen centre (the camera target): pan, then "Place here". Deleting asks by tapping twice (the frame has no modal dialogs). Not verified in a real browser against a live BlueMap when written.
**Full screen.** The Map tab (any proxied web UI) has a full-screen button between Reload and Open in new tab: the same iframe laid out over the whole window (no reload), left through an overlay button or Escape (the page forwards Escape with `postMessage` since key events do not cross the frame).

## BlueMap markers fix and full options (v0.4.7)
- **Why markers never appeared (v0.4.6).** The panel served them correctly, but the BlueMap web app builds a pin or text label by spreading `markerData.classes` into the element and reading `anchor.x` for the icon transform; our JSON had neither, so the app threw while creating the marker and (it swallows marker errors) dropped it. Areas, which need neither, were never affected. Now `renderMarker` always sends `classes` (default `[]`), `anchor` (pin `25,45`, label `0,0`) and `icon` (`assets/poi.svg`). Verified by loading the real BlueMap 5.29 web app behind the proxy in headless Chrome with every marker type.
- **Live event stream.** `maps/<id>/live/sse` is answered `404` by the proxy (it never ends, so the buffering proxy hung 30 s per connection, and while it is connected BlueMap stops polling for markers). The web app then polls markers (10 s) and players (1 s) itself.
- **All BlueMap options.** pin: `icon`, `anchor`, `classes`; label: `text`, `color`, raw `html`, `anchor`, `classes`; line: `lineColor`/`lineOpacity`, `lineWidth`, `depthTest`, `link`, `newTab`; area/volume: also `fillColor`/`fillOpacity`, `holes` (up to 16 rings), `y` or `minY`/`maxY`; all: `detail` (+ `detailHtml`), `listed`, `sorting`, `minDistance`, `maxDistance`. `color` stays as shorthand for line and fill color. On PATCH, `null` clears an optional field.
- **Restricted options.** `icon` (other than the default), `link`, `html` and `detailHtml` make the visitors' browsers load or run something the editor chose, so only panel users with operator access may set them; a public edit link gets `403 marker_option_restricted`. Everything else is open to edit links.
- **Editor.** The in-map editor creates and edits all five types: pin, text, line, area, volume. Lines, areas and volumes are drawn one point at a time with the crosshair bar (Add point / Undo / Done), with holes, colors, opacities, width, height range and a "More options" section for the rest.
